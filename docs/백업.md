## 2. 백업에 드는 것 — 코드를 뺀 "미리 구운 것"

tar 를 풀면 셋이다.

| tar 안 | 원래 자리 | 무엇 | 왜 백업하나 |
|---|---|---|---|
| `srv-data/` | `/srv/WegenersDream/data` | **운영 가공물 그대로** — 배경(정거원통·몰바이데), 지형, 해안선, 화석, 국경, 기온(Scotese), 최근 절 기온(PaleoClim `climate/pc_*.png`·`recent.json`, CC BY-NC-SA 4.0), `index.json` (216 MB 남짓) | 다시 만들려면 원본 3.2 GB·pygplates·10 분이 든다 |
| `pbdb/` | `~/projects/WegenersDream/data/sources/pbdb` | 그 가공물을 만든 **PBDB 원본**(`collections.csv`·`intervals.json`·`receipt.json`) | **PBDB 는 계속 자라 그날의 것을 다시 받을 수 없다.** 가공물과 짝이 맞게 같은 tar 에 둔다 |
| `state/` | `/srv/WegenersDream/state` | 화면에서 고친 명칭(`labels.json`, 있을 때) | 사람이 쓴 것이라 다시 만들 수 없다 |

**받기 전에 백업한다** — `fetch --refresh-pbdb` 가 지난 PBDB 사본을 덮어쓴다. 그래서 월요일의 tar 는 **갱신하기 전 한 주 동안
운영에서 돌던 자료**다.

## 4. 백업이 잘 되고 있나

```bash
curl -s http://paleolab/WegenersDream/healthz            # status·problems·refresh — 사람이 먼저 보는 곳(0.26.1)
cat /data/WegenersDream/logs/last_refresh.json         # result·step·note·backup·nas(같은 것이 /srv/WegenersDream/state/refresh.json 에도)
tail -40 /data/WegenersDream/logs/weekly_refresh.log
ls -la /data/WegenersDream/backups/ /nfs/temp-share/WegenersDream/backup/
sha256sum /data/WegenersDream/backups/WegenersDream.<날짜>.tar.gz /nfs/temp-share/WegenersDream/backup/WegenersDream.<날짜>.tar.gz
tar -tzf /data/WegenersDream/backups/WegenersDream.<날짜>.tar.gz | head
```

`last_refresh.json` 의 뜻:

- `"result": "ok"` 에 `"step": "deploy"` — 백업·NAS·갱신·운영 반영까지 끝남
- `"nas": "fail"` — NAS 가 안 붙었거나 옮기기·대조 실패. 로컬 백업은 있다. 갱신은 그대로 했다
- `"result": "fail"` — `step` 에서 멈췄다. **`check-repo` 면 paleoadmin 의 저장소 폴더가 `main` 이 아니거나 커밋 안 한 변경이 있다**
  (백업만 하고 가공하지 않는다). `fetch`·`build`·`verify` 면 운영은 지난 자료 그대로다

손으로 돌리기(paleoadmin):

```bash
~/projects/WegenersDream/deploy/host/weekly_refresh.sh --backup-only   # 백업(과 NAS)만
~/projects/WegenersDream/deploy/host/weekly_refresh.sh --no-deploy     # 가공까지, 운영에는 안 옮긴다
```

같은 날 다시 돌려도 덮어쓰지 않는다 — `WegenersDream.<날짜>.2.tar.gz`, `.3` …(0.26.1). 그 전에는 덮어썼고, 그 때문에 09-30 아침의
백업(갱신 전 PBDB 사본)을 잃었다(koprifossillab 034).

## 5. 되살리기

tar 를 풀어 셋을 제자리에 둔다. **가공물은 `index.json` 을 맨 나중에** — 컨테이너는 띄운 채로 두어도 된다(요청마다 파일을 읽는다).
아래는 09-30 의 tar 를 임시 폴더에 풀어 확인한 순서다.

```bash
B=/data/WegenersDream/backups/WegenersDream.20260930.tar.gz     # 또는 NAS 의 같은 파일
T=$(mktemp -d) && tar -xzf "$B" -C "$T" && ls "$T"                  # pbdb  srv-data  state

# 1) 운영 가공물
rsync -a --omit-dir-times --delete --exclude index.json "$T/srv-data/" /srv/WegenersDream/data/
rsync -a --omit-dir-times "$T/srv-data/index.json" /srv/WegenersDream/data/index.json

# 2) 명칭 덮어쓰기(있으면) — 비밀키는 건드리지 않는다
[ -f "$T/state/labels.json" ] && cp "$T/state/labels.json" /srv/WegenersDream/state/

# 3) 그 가공물의 PBDB 원본 — 다시 가공할 때 같은 자료로(다음 주간 갱신은 새로 받는다)
rsync -a "$T/pbdb/" ~/projects/WegenersDream/data/sources/pbdb/

~/projects/WegenersDream/deploy/host/smoke.sh http://172.16.116.98/WegenersDream/
curl -s http://127.0.0.1:8095/WegenersDream/healthz     # built_at·pbdb_retrieved_at 이 그 tar 의 것인가
```

- `--delete` 는 그 판에 없던 파일(예: 뒤에 생긴 것)을 지워 tar 와 똑같게 만든다. 판 사이에 가공물 구조가 바뀌었으면(예: 0.21.0 의
  `terrain/`) **지금 뷰어가 그 옛 가공물을 읽는지** 먼저 본다 — 뷰어와 가공물의 판이 맞아야 한다(HANDOFF "옛 가공물이면 다시 만든다")
- 서버를 통째로 잃었으면: 저장소 clone → `.venv` → `python -m pipeline fetch`(Zenodo 등) → tar 의 `pbdb/` 를 `data/sources/pbdb/`
  에 두고 → `/srv/WegenersDream/` 에 compose·`.env`(README "운영") → 위 1)·2) → 이미지는 Docker Hub 에서 `pull`
